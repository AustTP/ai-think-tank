### 1. What is being asked
Identify the root cause of the disk-full error (`Errno 28`) preventing git staging for `sandboxes/workroom-shared`. Produce a single saved report. The report must state:
- The specific volume that filled.
- Free space before and after the incident.
- The identifiers of the largest files or processes that consumed space.
- Whether the current staging code checks free space before writing.

### 2. Unknowns
- Current free space and total capacity of the target volume.
- Historical disk usage logs from the time of failure.
- The actual code path that executes the git staging for `sandboxes/workroom-shared`.
- Whether the failure was a one-time spike or a chronic leak.

### 3. Approach
1. Run `df -h` and `df -i` to identify the volume with zero or minimal free space.
2. Run `du -sh` on the parent directory and the target sandbox to find space hogs.
3. Check local logs for the specific timestamp of the `Errno 28` failure.
4. Inspect the codebase for the git staging logic. Search for `git`, `index-pack`, or `object` writes. Verify if a pre-check for available space exists.
5. Draft the report with findings. Save it to the mandated path.

### 4. Risks
- Stale logs.
- Permission denied when accessing certain file paths.
- The volume may have already been cleaned since the failure, removing the evidence.
- Misinterpreting temporary files as the primary cause.

### 5. Done when
